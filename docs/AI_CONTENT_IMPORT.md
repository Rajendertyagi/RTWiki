# AI Content Import

This document defines how RTWiki receives rich study notes generated by external AI tools. It specifies the **RTWiki note-package** (`.rtwiki.zip`) contract, the **shared import pipeline** that every entry path uses, and the **localhost import API**. It is the authoritative reference for requirements R-040–R-063 and acceptance criteria AC-063–AC-086. See also [ADR-006](adr/ADR-006-rich-content-and-import-contract.md) (rich-content model) and [ADR-007](adr/ADR-007-sandboxed-custom-content.md) (sandboxed custom content).

## 1. Purpose

RTWiki is designed first and foremost to receive AI-generated rich pages. An external AI tool produces a page (text, formulas, pictures, cards, tabs, callouts, tables, diagrams, mind maps, optional custom HTML/CSS/JS). RTWiki then imports, validates, previews, and stores it as canonical BlockNote JSON. Markdown and raw HTML remain supported as **lossy fallbacks** when a package is not available; they are not the preferred format.

## 2. Three-Level Rich-Content Model

| Level | Name | Description |
|-------|------|-------------|
| L1 | Native RTWiki custom blocks | First-class BlockNote custom blocks (cards, tabs, callouts, grids, formulas, diagrams, images). Preferred representation. |
| L2 | Versioned `rt-*` HTML | RTWiki-defined HTML vocabulary for structures mapped to native blocks or preserved as sanitized HTML. |
| L3 | Sandboxed custom HTML/CSS/JS | Per-page custom content rendered only in an isolated sandbox (see [ADR-007](adr/ADR-007-sandboxed-custom-content.md)). |

## 3. The RTWiki Note-Package (`.rtwiki.zip`)

The preferred interchange format is a ZIP archive with this layout:

```text
package.rtwiki.zip
├── manifest.json          # required: schema version + page list
├── content.json           # required: canonical BlockNote JSON per page (L1)
├── page.html              # optional: rich-HTML source per page (L2 fallback)
├── style.css              # optional: per-page scoped CSS (L3)
├── script.js              # optional: per-page sandboxed JS (L3)
└── assets/                # optional: images and binaries, localized on import
    └── <uuid>_<name>
```

### 3.1 `manifest.json`

```json
{
  "schemaVersion": "1",
  "generator": "ExampleAITool/2.3",
  "createdAt": "2026-08-19T10:00:00.000Z",
  "pages": [
    {
      "id": "notes-algebra-intro",
      "title": "Algebra Intro",
      "contentRef": "content.json#/pages/0",
      "htmlRef": "page.html#/pages/0",
      "styleRef": "style.css",
      "scriptRef": "script.js",
      "assets": ["assets/uuid_pic1.png"]
    }
  ]
}
```

- `schemaVersion` is a required string. Unknown or incompatible versions are rejected.
- `pages` is a required, non-empty array. Each entry references its content and optional assets.

### 3.2 `content.json`

Canonical RTWiki-extended BlockNote JSON. One document per page, using typed custom blocks where possible (L1). This is what is stored.

### 3.3 `page.html` (optional)

The original rich-HTML source retained when conversion to canonical JSON was **not lossless**. Never the primary view; used for recovery and review.

### 3.4 `style.css` / `script.js` (optional, L3)

Per-page custom CSS/JS. They are **never** executed in the main application context. `script.js` runs only inside the sandbox described in [ADR-007](adr/ADR-007-sandboxed-custom-content.md).

### 3.5 `assets/`

Binary assets. On import they are copied into `data/attachments/` under a safe generated filename and all references are rewritten to the localized path.

## 4. Import Paths (One Shared Pipeline)

All four entry paths use the **same** pipeline — there are no parallel implementations:

| Path | Trigger |
|------|---------|
| Paste | User pastes from an AI response or browser |
| File drop | User drags a `.rtwiki.zip`, `.html`, or `.md` onto the window |
| File import | User picks a file via a dialog |
| Localhost API | An external AI tool calls `POST /api/v1/import/pages` (see §7) |

### 4.1 Pipeline Stages

```text
adapter → validation → sanitize → asset localization → convert → preview → canonical JSON → transactional save
```

1. **Adapter** — detects the source format (note-package, HTML, Markdown, or BlockNote JSON) and normalizes it.
2. **Validation** — verifies manifest, size, and `schemaVersion`; applies ZIP-bomb and path-traversal guards for packages.
3. **Sanitize** — runs DOMPurify on any HTML; strips scripts from pasted/imported HTML.
4. **Asset localization** — extracts referenced images and writes them to `data/attachments/`, rewriting references.
5. **Convert** — maps source structures to the RTWiki-extended BlockNote schema (native blocks + `rt-*` HTML where needed).
6. **Preview** — renders a sanitized preview and collects warnings (unknown blocks, stripped scripts).
7. **Canonical JSON** — produces the stored BlockNote JSON document.
8. **Transactional save** — writes pages and assets inside one transaction; on failure, rolls back so existing data is untouched.

## 5. Validation, Safety, and Integrity

| Check | Behaviour |
|-------|----------|
| Manifest validation | Missing/invalid `manifest.json` or `schemaVersion` → reject with a clear error; no partial write. |
| ZIP-bomb protection | Package and uncompressed size are limited by `config.import.maxPackageBytes` (default 50 MB); exceeded → reject before full extraction. |
| Path traversal prevention | Every archive entry name is canonicalized; entries escaping the package root are rejected. |
| Transactional import | All pages/assets are written, or none. A failed import leaves existing pages unchanged. |
| Rollback | A failed or rejected import does not alter existing pages; the prior workspace state stays intact. |
| Unknown-block preservation | Unrecognized block types are stored (not deleted) and rendered with a safe fallback, flagged for review. |
| Rich-HTML fallback | When conversion is not lossless, the original HTML is retained in `pages.content_html_fallback`. |
| No silent loss | Warnings are surfaced in the preview; content is never dropped without a visible flag. |
| Image localization | Imported images are stored under `data/attachments/` and references rewritten; they render offline. |
| Preview before save | The user sees sanitized output and warnings before the import is committed. |

See [SECURITY.md](SECURITY.md) for the threat model and enforcement details.

## 6. Canonical Storage

Imported content is stored as described in [DATA_MODEL.md](DATA_MODEL.md):

- `pages.content` — RTWiki-extended BlockNote JSON (versioned via `content_schema_version`).
- `pages.content_html_fallback` — nullable original rich-HTML source retained for non-lossless conversions.
- `attachments` — localized images under `data/attachments/`.

## 7. Localhost Import API

`POST /api/v1/import/pages` accepts AI-generated pages and note-packages.

- **Loopback only.** Bound to `127.0.0.1`; accepts no cross-origin requests (CORS disabled). Only the local machine may call it.
- **Request body.** `multipart/form-data` (a `.rtwiki.zip` or source file) or `application/json` (a pre-built content document), with a client-supplied `requestId` for idempotency.
- **Size limits.** Enforced before parsing (ZIP-bomb protection).
- **Schema validation.** Malformed bodies return `4xx` and write no data.
- **Idempotency.** Repeated identical requests (same `requestId`) do not create duplicate pages.
- **Custom JS confinement.** Any `script.js` in the package is confined to the sandbox; it has no database, filesystem, or network access.
- **Response.** `201 Created` with the created page ids, or `207 Multi-Status` with per-page warnings (e.g., unknown blocks preserved).

This endpoint is **documented now and implemented in the MVP** as a target; it is not a cloud or network feature.
