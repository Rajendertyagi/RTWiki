# Known bugs and open issues

A running list of defects found and left unfixed, so they are not rediscovered later.
Every entry records what was **measured**, and what remains unproven is said plainly.

Newest first. Last reviewed: 2026-09-26, on branch `docs/trilium-uiux-spec`.

---

## 1. The dev database is full of test data, which breaks four browser tests

**Impact: high — it is the only thing preventing a trustworthy full-suite result.**

The local database holds roughly 6,900 pages, nearly all generated by the browser test suite
(`Bulk …`, `VB …`, `Toolbar …`, `NarrowInsert …`). Tests that read pages without pagination, or
that look for a dashboard card by title, degrade as it grows.

**Measured:** four `visual-blocks` tests time out at the 30s limit —
`flowchart: insert → render → edit source → save → reload` (:182), `mind map: insert → render →
edit → reload` (:230), `rapid tab/page switching does not lose block changes` (:388), and
`browser reload restores the page and rendered blocks` (:425). Symptoms are
`request.get('/api/pages')` timing out, an `Open <title>` card not present on the visible
dashboard page, and the `Pages` heading never rendering. Which tests time out **varies between
runs** (2 on one run, 4 on another), which is why this was not previously attributed correctly.

**Not caused by** the toolbar overflow-menu fix in `06205a5`; those tests do not touch
`toolbar-more`.

**Next step:** purge auto-generated test pages, keeping the owner's own. This needs an explicit
decision because it deletes data — see item 8.

## 2. The rich toolbar's "more" menu cannot be operated by keyboard

**Impact: medium — a keyboard or screen-reader user cannot reach the overflowed controls.**

The overflow menu reuses the toolbar's tail controls whole, as bare Mantine `ActionIcon`s.
`MenuDropdown.mjs:27` moves focus by querying `[data-menu-item]`, and the menu's type-ahead
queries the same selector, but the moved controls carry neither. Consequences: pressing Enter
lands focus on Mantine's initial-focus placeholder, and arrow keys move nowhere.

**Measured** by static reading of the installed Mantine build and reproduced in the browser.
Not fixed by `06205a5`, which addressed dismissal and focus theft but not focus movement.

**Not a small fix.** Either the overflowed controls become real `Menu.Item`s — which means
declaring ~24 controls again and turning a compact icon row into a vertical list, breaking the
"moved whole, nothing re-implemented" property `useToolbarOverflow` depends on — or each control
carries `data-menu-item` individually. The ARIA structure is also already wrong: the dropdown is
`role="menu"` while its children are icon buttons with no `menuitem` role.

**Next step:** a design decision, not a patch. Needs manual screen-reader testing (NVDA /
VoiceOver) to confirm the outcome.

## 3. A comment in the toolbar source contradicts the code

**Impact: low, but actively misleading.**

`src/web/features/rich-editor/rich-toolbar.tsx:628` still reads:

> The row scrolls horizontally on narrow screens instead of …

The row does **not** scroll. `useToolbarOverflow` measures the available width and moves whatever
does not fit into the trailing more menu. The comment predates that change and was noticed during
the same work but left alone rather than rewritten inside a test-fixing commit.

**Next step:** one-line correction.

## 4. Nothing tests the `style-src` CSP directive, which Mermaid silently depends on

**Impact: medium — a future CSP tightening would break every diagram with no test failing.**

`src/server/app.ts:34` sets `style-src 'self' 'unsafe-inline'`, verified on the wire against a
running server. Mermaid injects `<style>` elements and relies on that directive. But
`tests/foundation.test.ts:190` asserts only `default-src 'self'`, so the directive every diagram
depends on is untested.

**Next step:** add an assertion for `style-src` in `foundation.test.ts`.

## 5. An unused autosave binding sits next to the save-status code

**Impact: low.**

`src/web/features/visual-pages/mermaid-workspace.tsx:104` destructures `retry` from
`useAutosave` and never uses it. Biome reports `noUnusedVariables`; the error is **pre-existing**

`visual-pages.pwspec.ts:148`, which tests the save indicator — possibly related, uninvestigated.

**Next step:** use it or remove it; do not "fix" it opportunistically.

## 6. Six Mermaid diagram types are unverified on 12.0.0

**Impact: low today, higher once a wider template picker exists.**

Of 32 fixture types rendered against mermaid 12.0.0, **25 rendered with correct, distinct
identities**. The remainder:

- **`gitGraph` and `venn`** changed the rendered markup not at all. **Undiagnosed.**
- **`quadrantChart`, `architecture`, `radar`, `treeView`, `zenuml`** produced a 24×24 SVG with no
  error marker. No error was raised, so the likeliest explanation is that the fixtures are
  incomplete for those types rather than that Mermaid is broken. `zenuml` is an *external* diagram
  requiring `@mermaid-js/mermaid-zenuml`, which RTWiki does not depend on, so it should not have
  been in the list.

**None of these are reachable from the UI today.** The picker offers flowchart, sequence, class,
state, er and timeline, plus mind map, and every one of those is verified working on 12.0.0.

**Next step:** fix the fixtures first, then re-measure. Do not change application code on the
strength of a fixture failure.

## 7. Mermaid 12 dark mode was asserted, never looked at

**Impact: low, but it is an unverified claim sitting in an ADR.**

Mermaid 12 ships `redux-color`/`neo` as the default appearance. `MERMAID_CONFIG` pins
`look: 'classic'` to hold v10's appearance, and that pin is unit-tested. But `look` is now
threaded into every Mermaid stylesheet, and v12 added gradient behaviour, so **whether dark mode
still matches the rest of the application has not been visually confirmed**. The pin is
well-founded; the appearance is unverified.

**Next step:** open a diagram page in dark mode and compare it against the app's theme.

## 9. There is no local script for the browser suite

**Impact: low.**

`package.json` defines `"test": "bun test"` for the unit suite. There is no `test:browser`
script, so the Playwright suite is invoked by hand with a long command and a `PLAYWRIGHT_PORT`.
CI does run browser tests (`.github/workflows/build.yml` references Playwright), so this is a
convenience and consistency gap rather than an absence of gating.

**Next step:** add a `test:browser` script.

## Appendix — harness traps that cost real time

Not product defects, but each produced a confident wrong answer before being caught. Recorded so
they are not repeated. The underlying lesson: **a red result from a harness built in the current
session is a fact about the harness, not about the application.**

- **Detecting a Mermaid render failure by searching the SVG markup for `error-icon`.** Mermaid's
  `<style>` block *defines* `.error-icon` and `.error-text` in **every** SVG, success or failure,
  so the check reports an error for every diagram. Match an actual error **element** instead.
- **Using node ids as text markers.** Ids live in attributes, not `textContent`. This reported
  `flowchart` as broken when flowchart demonstrably works.
- **Assigning a variable inside `page.evaluate` and reading it in Node.** The assignment happens in
  the browser and never propagates. Thirty-two "passing" results came back with empty names.
- **`getBBox()` on Mermaid mindmap nodes** returns pre-transform local coordinates, because
  Mermaid transforms the group, so geometry is not comparable across versions. A screenshot is
  the reliable signal.
- **A readiness check satisfied by the pre-existing render.** Waiting for a non-empty
  `aria-roledescription` passes instantly on whatever is already on screen, so the check never
  waited for the new source to render.
- **Treating "Saved" in the status bar as proof a save happened.** It is also shown for a clean
  page, so the assertion was vacuous and the test then raced the 2000ms autosave debounce.
- **Expecting `aria-roledescription` on every diagram type.** `gitGraph`, `quadrantChart`, `venn`,
  `architecture`, `radar` and `treeView` do not emit it, so keying on it reports working diagrams
  as broken.
- **The dev server serves the prebuilt `build/web`.** Browser tests only see source changes after
  `bun run build:web`. A run against a stale bundle looks like a failing fix.
- **Simulating a bug inside a fixed build does not reproduce it.** A real pre-fix build was needed;
  the simulation produced a false negative, because the fix had changed the mechanism responsible.
