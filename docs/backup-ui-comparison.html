Defect found while comparing — the table headers do not match the cells

backup-panel.tsx:291-296 builds the header from the same PERIOD_LABEL constants that label the toggle rows above:

<Table.Th>{PERIOD_LABEL.daily}</Table.Th> → <Table.Th>{UI_TEXT.backupRestore}</Table.Th> → empty

The body at :303-314 puts date + size in the first cell, filename in the second, and the Restore button in the third.

So the column headed Daily shows a timestamp, and the column headed Restore shows a filename. The header row was carried over from the toggle list and never revised when the table was written.

This is very likely caused by our one extra feature. The per-slot interval field made the toggle rows a list of period labels, and the table was then built from those same labels. A per-slot table needs headers like Last taken / Size / File / —.

It is also consistent with the browser spec timing out at backup-panel.pwspec.ts:57: the tests assert on testids, not on a table a person could read.

Why the gap exists — three different reasons

  • Deliberate. Encryption, compression and the password flow are gone by your decision. But dropping encryption also removed the badges and the encrypted-or-local fallback rule that depends on it — roughly six Trilium features removed by one decision, and the plan never said so.
  • Accidental, and it went the other way. Configurable per-slot intervals is a feature Trilium does not have. It is probably what coupled the toggle rows to the table headers.
  • Never built. Location picker, delete-one-backup, the "newest X ago" summary, and the badges. Not declined — simply absent.
  • On size, we are not far behind. 329 lines against their 467 + 336. The extra ~470 lines are almost entirely location, compression and encryption — the part you declined.

What a user cannot do today in RTWiki

  • Tell when a backup last ran. The column that would show it is mislabelled.
  • Tell which file a row refers to without reading the Restore button's context.
  • Delete a bad backup. With three fixed slots, a corrupt daily is overwritten by tomorrow's run and there is no way to clear it. Ironic, because choosing fixed slots was partly to protect against exactly that.
