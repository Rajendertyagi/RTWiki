# ADR-006: Rich-Content Model and Note-Package Import Contract

| Field | Value |
|-------|-------|
| **Status** | **Accepted** |
| **Date** | 2026-08-19 |
| **Deciders** | Project Owner, Lead Developer |
| **Supersedes** | — |

## Context

RTWiki's primary purpose is to receive rich study notes generated by external AI tools — text, formulas, pictures, cards, tabs, callouts, tables, diagrams, mind maps, and optional custom HTML/CSS/JS — and store them as structured, visually editable pages. The earlier ADRs established BlockNote JSON as the canonical format ([ADR-004](ADR-004-canonical-block-json-format.md)) and the frontend stack ([ADR-003](ADR-003-react-blocknote-mantine.md)), but they did not define how rich AI-generated content is modelled, how it arrives, or how non-BlockNote content is handled safely.

The questions this ADR resolves:

- What richness levels exist, and how do they relate to the canonical BlockNote JSON?
- What is the preferred interchange format for AI-generated pages?
- How do all import paths (paste, drop, file, API) share one pipeline?
- How is custom HTML/CSS/JS permitted without compromising the offline, localhost-only security model?

## Decision

### Three-Level Rich-Content Model

Content is organised into three richness levels:

- **L1 — Native RTWiki custom blocks.** First-class BlockNote custom blocks owned by the block registry: cards, tabs, callouts, grids, formulas, Mermaid diagrams (including mind maps), and images. These are the preferred representation and survive import/round-trip editing without loss.
- **L2 — Versioned `rt-*` HTML vocabulary.** A RTWiki-defined, versioned set of HTML elements and attributes (`rt-*`) used when a rich structure maps cleanly to a native block or must be preserved as sanitized HTML that the editor does not yet model natively. It is converted toward L1 where possible and retained as sanitized HTML otherwise.
- **L3 — Sandboxed custom HTML/CSS/JS.** Optional per-page custom HTML/CSS/JS rendered only inside an isolated sandbox (see [ADR-007](ADR-007-sandboxed-custom-content.md)). It is never authored into the main application context.

### Note-Package Contract

The preferred interchange format for AI-generated pages is the **RTWiki note-package** (`.rtwiki.zip`). It contains:

- `manifest.json` — schema `version`, package metadata, and a list of pages.
- `content.json` — canonical BlockNote JSON per page (L1 preferred).
- `page.html` — optional rich-HTML source per page (L2 fallback retained when conversion is not lossless).
- `style.css` — optional per-page scoped CSS (L3).
- `script.js` — optional per-page sandboxed JS (L3).
- `assets/` — images and other binary assets, localized to `data/attachments/` on import.
- `schema` — a declared `schemaVersion` enabling startup migration.

### Centralized Import Pipeline

All content entry paths share one pipeline:

```
adapter → validation → sanitize → asset localization → convert → preview → canonical JSON → transactional save
```

Paste, file drop, file import, and the localhost import API all flow through this pipeline. There are **no parallel import implementations**.

### Localhost Import API

A documented `POST /api/v1/import/pages` endpoint accepts AI-generated pages and note-packages. It is bound to the loopback interface only, accepts no cross-origin requests, enforces size limits before parsing, validates the manifest schema, checks entry names for path traversal, is idempotent per client request id, and confines any custom JS to the sandbox. It is **documented now and implemented in the MVP** as a target endpoint.

### Modular Registries and Composition Root

Block types, import adapters, export adapters, renderers/editors, sanitization policies, asset storage, theme/token providers, package validators, and the schema migrator are all registered in their respective registries. A single composition root wires them together. A future AI-provider adapter also registers here rather than being hard-wired. There is **no central switch statement** over block types.

## Alternatives Considered

| Alternative | Reason for Rejection |
|------------|---------------------|
| Markdown as the primary rich format | Markdown cannot faithfully represent cards, tabs, callouts, grids, or custom HTML/CSS/JS; it degrades rich AI output. It remains a fallback only. |
| Store arbitrary HTML directly in the database | Breaks the canonical-format decision ([ADR-004](ADR-004-canonical-block-json-format.md)); unsafe and unsearchable. |
| One monolithic importer with switch statements | Hard to extend; contradicts the modular registry approach and the owner's "define once, reuse everywhere" principle. |
| Allow custom JS in the main application context | Defeats the offline, localhost-only security model; requires a sandbox (see [ADR-007](ADR-007-sandboxed-custom-content.md)). |

## Consequences

**Positive:**
- AI-generated rich content is a first-class citizen, not a degraded Markdown conversion.
- One pipeline means consistent, testable behaviour across all entry points.
- The note-package gives external AI tools a stable, versioned contract.
- Modular registries make new block types and adapters easy to add safely.

**Negative:**
- The import pipeline and package validator are more complex than a simple Markdown paste.
- L3 custom content requires a sandbox implementation and careful CSP tuning.

**Neutral:**
- Markdown and HTML remain supported as lossy fallbacks when no package is available.

## Risks

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Malicious package (ZIP bomb, path traversal) | Low | Size limits before parse; manifest validation; canonical-path confinement (see [SECURITY.md](../SECURITY.md)). |
| Non-lossless conversion drops content | Medium | Retain original rich-HTML source; preserve unknown blocks; show preview warnings. |
| Sandbox escape | Low | Strict `sandbox` attributes + CSP; no same-origin; no network; reviewed against [ADR-007](ADR-007-sandboxed-custom-content.md). |
| Schema drift between AI tool and app | Medium | Declared `schemaVersion`; startup migrator; reject incompatible versions. |

## Revisit Conditions

This decision should be revisited if:
- A fundamentally better rich-content interchange format emerges that the `rt-*` vocabulary cannot express.
- The security model for L3 custom content proves impractical on the Windows portable target.
- The owner decides to support cloud AI chat (would require a new ADR and an explicit decision — see [ROADMAP.md](../ROADMAP.md)).
