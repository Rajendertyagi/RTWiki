## 1. Project Overview

**What it is.** A local-first, offline personal knowledge wiki that runs entirely on one Windows PC. No accounts, no internet at runtime, no cloud. **VERIFIED** from `README.md` and `src/server/config/index.ts` (loopback bind to `127.0.0.1:8080`).

**Primary purpose — two, and they conflict.** The README says RTWiki "is designed first and foremost to **receive rich study notes generated by external AI tools**" and store them as structured pages. But [AI_CONTENT_IMPORT.md](AI_CONTENT_IMPORT.md) describes that entire import pipeline as unbuilt, and [AGENTS.md](../AGENTS.md) confirms zero import code exists. **The AI-receiving workflow is the product vision, not the product.** What is built is a general block-based wiki with a Markdown pipeline, a calendar, attachments, and now backup/restore.

**Target users.** One family sharing a single PC. Stated in `README.md`, [SECURITY.md](SECURITY.md) §1 ("runs entirely offline on a shared family PC"), and [ADR-001](adr/ADR-001-browser-first-local-application.md).

**Development status — read the README carefully, it overstates.** `README.md` says "**MVP foundation implemented**", but the same document's tech table names **Drizzle ORM and `@blocknote/diagram-block`, neither of which is installed**. [ADR-018](adr/ADR-018-documented-vs-built.md) exists precisely because the docs once described an architecture that was never built. **The README's own table is wrong. VERIFIED** by checking `package.json`.

**Already built:** pages and hierarchy, BlockNote rich editor, Markdown pages (micromark) with math/columns/diagrams, calendar with recurrence and notifications, attachments (images, documents), search, trash, tabs, theming, autosave, settings, desktop shell, and — on this branch — backup/restore.

**Planned, not built:** the shared import pipeline, the block registry, version history, LAN access, a mind-map editor, export formats, AI chat.

## 4. Architecture

**Modular monolith** ([ADR-002](adr/ADR-002-bun-hono-sqlite.md)): one Bun process, one Hono app, one SQLite file. Three source roots:

| Root | Files | Contents |
|---|---|---|
| `src/server/` | 39 | `routes/` 8, `services/` 3, `repositories/` 2, `database/` 2, `backup/` 4, `attachments/` 5, plus `config/`, `settings/`, `logging/`, `utils/`, `shutdown-coordinator.ts` |
| `src/web/` | 169 | `features/` 126, `layout/` 8, `services/` 8, `components/` 5, `hooks/` 5, `theme/` 3, `diagnostics/` 3, `util/` 5 |
| `src/shared/` | 19 | `contracts/` 4, `schemas/` 10, `constants/`, `schedule/` 2, `attachments/` 2 |

**Layering: routes → services → repositories → database.** Routes validate and delegate; services hold business rules; repositories own SQL. **VERIFIED** across `routes/pages.ts` → `services/page-service.ts` → `repositories/page-repository.ts`.

**Shared code** via tsconfig paths `@rtwiki/shared/*`, `@rtwiki/server/*`, `@rtwiki/web/*` and a matching Vite alias. `src/shared/constants/index.ts` is the single source for ~55 named constants; `AGENTS.md` §5 requires this and forbids restating values.

**Configuration** derives all paths from the **executable's** directory, never the working directory ([ADR-005](adr/ADR-005-portable-data-layout.md)). `config/index.ts` exports `createConfig`, `resolveRuntimePaths`, `joinPaths`, `dirname`. Settings persist as JSON beside the database: `server.json`, `desktop.json`, and now `backups.json`.

**Data flow.** React state in `App.tsx` → hooks (`use-pages-controller`, `use-schedule-controller`) → thin API clients (`services/pages-api.ts`, `schedule-api.ts`) → `fetch` → Hono routes → services → repositories → `bun:sqlite`. Autosave is a debounced controller (`rich-editor/use-autosave.ts`, `PROVISIONAL_AUTOSAVE_DEBOUNCE_MS` = 2000).

**Architectural boundaries that matter:**

- **BlockNote JSON is canonical page storage**; HTML and Markdown are conversion formats ([ADR-004](adr/ADR-004-canonical-block-json-format.md))
- **No parallel import paths** — `AGENTS.md` §4 mandates one shared pipeline
- **`bun:sqlite` only, hand-written parameterised SQL, no ORM** ([ADR-002](adr/ADR-002-bun-hono-sqlite.md))
- Markdown pages use a separate `{version, markdown}` content schema from BlockNote pages
- Unknown blocks are preserved via `containUnknownBlocks` (`rich-editor/document.ts`)

## 7. Authentication & Security

**There is no authentication.** No users, no passwords, no sessions, no login. Single-user by design, documented in [ADR-001](adr/ADR-001-browser-first-local-application.md) and [SECURITY.md](SECURITY.md) �1. Anyone who can reach the loopback port has full access. **A deliberate product decision, not a gap.**

**What protects the loopback service instead � all four VERIFIED:**

1. **Host header allowlist on every request.** `src/server/utils/request-host.ts`, registered at `app.ts:163-167`. Stops DNS rebinding, where the browser sends no `Origin` and no `Sec-Fetch-Site` so `isSameOrigin` would otherwise accept. Cites CVE-2024-28224 (Ollama) and CERT/CC VU#652514. Deliberately permissive: a check that blocks a real user is treated as the worse bug.
2. **`isSameOrigin()` on unsafe methods only.** `utils/request-origin.ts`, `app.ts:170`. GET is exempt so health checks and the desktop shell keep working.
3. **Per-process shutdown token.** Header `x-rtwiki-shutdown-token`, compared with `timingSafeEqual`. Required by `POST /api/shutdown` and `POST /api/backup/restore`.
4. **Security headers.** Hono `secureHeaders` at `app.ts:144`, CSP at `:53-64`.

**Known gaps, all documented in `AGENTS.md` �9:**

- `Cache-Control` is set at exactly four sites; **the entire JSON API returns no cache directives**
- A per-route `bodyLimit` exists on attachments; **there is no global request ceiling** � the right place would be a `bodyLimit` in `createApp()`, unbuilt
- `PRAGMA synchronous` is never set, so `VACUUM INTO` output durability rests on a compile flag inside Bun's SQLite
- LAN binding is forbidden until the cross-origin work is signed off

**Input validation:** zod schemas in `src/shared/schemas/` (10 files), byte-bounded strings, per-route body caps in `src/shared/constants/index.ts`, `sanitize-path.ts` for filesystem paths, and DOMPurify on the **Markdown render path only** � not on pasted HTML, the raw-HTML page, or diagram output.

**Secrets:** none. No `.env` consumption in `src/`. `AGENTS.md` �7 forbids `AppData`, `%LOCALAPPDATA%`, and environment-variable data overrides.

## 8. Database

**Eight tables**, all defined in the single file `src/server/database/migrations.ts`; eight name-keyed migrations run at startup from `bootstrap.ts`.

**`pages`** � `id TEXT PRIMARY KEY`, `title`, `content` (JSON, page-type-specific), `page_type`, `parent_id` (self-FK, `ON DELETE SET NULL`), `position`, `created_at`, `updated_at`, `deleted_at` (soft delete), `version` (single integer). Adjacency-list hierarchy. **`id` is TEXT, so `pages` is a rowid table** � see �17.

**`page_links`** � `source_id`, `target_id`. No FK constraints; broken links are deliberately preserved (`migrations.ts:81-82`).

**`search_index`** � `page_id`, `title`, `content`, mirrored to the unused `search_index_fts` virtual table.

**`attachments`** � metadata plus a `data BLOB` column ([ADR-014](adr/ADR-014-blob-stored-image-bytes.md)). `stored_name` is retained as `UNIQUE` when any row still has `data IS NULL`.

**`schedule_entries`**, **`reminders`**, **`schedule_presets`**, **`_migrations`**.

**Connection lifecycle** � `src/server/database/index.ts`. WAL plus `foreign_keys = ON` at every connection; `checkIntegrity()` at startup, now try/catch-wrapped so a throw counts as failure. **`closeDatabase()`** is idempotent and exists for the restore swap.

**Important queries � five tie-break on rowid, and `VACUUM INTO` may renumber it:**
- `page-repository.ts:365`, `:382` � `ORDER BY updated_at DESC, rowid DESC`
- `page-repository.ts:430`, `:435` � `ORDER BY position, rowid` (**this is page-tree order**)
- `migrations.ts:67` � a one-time data fix, not a live dependency

| Commit | Scope |

**Implementation.** `src/server/backup/` � `backup-service.ts` 11.3 KB, `restore-service.ts` 8.6 KB, `schedule.ts` 5.2 KB, `validation.ts` 8.8 KB. UI in `features/settings/backup-panel.tsx` and `restore-confirm-modal.tsx`. Routes in `routes/backup.ts`. Constants from `src/shared/constants/index.ts:161`.

**Mechanism: `VACUUM INTO`** against the live database, chosen because a file copy of a WAL database passes `integrity_check` while having lost committed data still in the `-wal` sidecar. **Three fixed slots** (`BACKUP_SLOTS`), each overwriting only itself, with **deliberately no retention code**; intervals configurable, 1 hour to 8760.

**Settings persist to `data/backups.json`**, not `server.json`, because `writeServerPort` replaces `server.json` wholesale and sharing it would erase the schedule on every port change.

### What is genuinely right

- **The WAL sidecars move with the database.** `PRE_RESTORE_SIDECARS = ['', '-wal', '-shm']`. Replacing only the main file leaves the previous database's `-wal` beside the new one; SQLite treats a mismatched WAL as a hot journal and replays it, writing the old wiki's pages over the restored one. Silent, and the restore would appear to have worked. **Not in the design document; the most important thing the implementation added.**
- **The connection closes before anything moves** (`restore-service.ts:153`). SQLite on Windows does not open files with `FILE_SHARE_DELETE`, so renaming a live database fails `EBUSY`. Ordering is load-bearing.
- **Rollback on a failed copy** � the previous wiki is renamed back; if that also fails the error names where the pre-restore copy is. Nothing is ever deleted.
- **The backup is copied, not consumed** � restoring a slot leaves it intact and a retry is possible.
- **Validation opens its own read-only connection** (`validation.ts:180`), never the live one.
- **A throw from any validation step is a refusal, never a pass** (`:88-94`, plus a whole-sequence catch at `:195`).
- **Path containment uses `basename` then `path.relative`**, not a prefix test, which fails at a drive root (`restore-service.ts:68-83`).
- **Windows `rename` over an existing file was measured**, not assumed; no delete-then-rename fallback was written because none is needed.
- **A dead branch was removed rather than shipped** � an "is this the live database?" check that containment already made unreachable.

### Two gaps, both verified

1. **The written backup is never validated.** `createBackup` moves the `.partial` onto the slot and returns `ok`; `validateBackupFile` is not called on the result, confirmed by search. A backup can land corrupt and go unnoticed until the restore, when it is the only copy that exists. SQLite's guidance is that a backup never confirmed "is indistinguishable from no backup at all", and verification must run against the **completed image**. **The previous good backup is already gone by that point**, which makes this urgent rather than tidy.
2. **The browser spec has never passed.** `test-results/.last-run.json` records `status: "failed"` with three failed tests. `backup-panel.pwspec.ts:57` times out at 30 s on `getByTestId('backup-enabled-monthly')` � the locator resolves and the element is visible, enabled and stable, then the click hangs. Five tests declared. **This is the only feature whose end-to-end behaviour is unproven**, and restore is the worst possible candidate for unit-only confidence: the round trip is only real through the actual app, the actual shutdown and an actual reopen.

Search is `GET /api/pages?q=` matching `search_index` with `LIKE`. **The FTS5 table exists and is never queried � do not describe search as FTS5-backed.** Strict TypeScript. **BlockNote JSON is canonical storage.** A modular block architecture with a registry is required and **is not met** � `rich-editor/schema.ts` is a hand-maintained list. Lazy-load heavy diagram and math features. Pin stable versions, no floating majors.

**Portable filesystem (�7).** All paths derive from the **executable's** directory, never the working directory. **No `AppData`, no `%LOCALAPPDATA%`, no environment-variable data override.** No silent fallback to another directory � show a clear error and stop. Define directory and file names **once**. Create missing directories at startup. Check write access. Keep SQLite **WAL** and **SHM** inside `data/`. **Include the database and attachments in backups; exclude logs. NOW BUILT** (`src/server/backup/`) � one bare SQLite file via `VACUUM INTO`, three fixed slots, no retention code, and a **refusal** when a database is mid-migration. Rotate and limit logs; **never log private page or pasted content.**

**Coding standards (�8).** Strict TypeScript, no unjustified `any`. No magic strings or numbers. Small modules, explicit interfaces at boundaries. Reusable components; **no inline CSS except documented runtime-calculated exceptions.** Mantine theme tokens for visual values; a central UI text dictionary. Parameterised queries only, versioned migrations, transactions for multi-step writes. Central error handling with non-technical user-facing messages. Safe filenames and path handling, atomic file operations where practical. Debounced autosave with a visible indicator. **Comments that explain decisions, not obvious syntax; no swallowed exceptions.** No runtime CDN dependency; no secrets in source control. The 2000 ms autosave debounce and 50 MB attachment limit are **provisional centralised defaults** � `PROVISIONAL_AUTOSAVE_DEBOUNCE_MS` and `PROVISIONAL_MAX_ATTACHMENT_SIZE_BYTES`. The 50 MB figure is the **attachment** limit only.

**Security (�9).** Localhost-only binding; **never `0.0.0.0` without authorisation.** DOMPurify before HTML reaches the editor or database. Mermaid's `securityLevel: "strict"` with `htmlLabels: false`; **the 21 `DIAGRAM_TEMPLATES` are not a security boundary** � a user can type arbitrary Mermaid. Extension, MIME and size validation; path-traversal protection. No execution of uploaded documents. No arbitrary scripts from pasted HTML. Custom HTML/CSS/JS runs only in a sandboxed iframe. Reject cross-origin requests and validate the `Host` header. Set security headers. Enable foreign keys and wrap multi-step operations in transactions. **Treat a throw as failure in any validator.** Validate a backup before restoring. **Logs must contain no private content.** **LAN binding requires a separate authorised phase and security review.**

**Development/verification separation (�10).** The manager issues an implementation-only prompt; the agent changes only the authorised scope and reports; the manager reviews; a **separate verification prompt** follows. **An implementation agent must not claim verification it did not perform**, and must report commands run, checks skipped, and known limitations honestly.

**Quality gates (�11).** Formatting, linting, type checking, risk-based tests, frontend and backend builds, Windows executable compilation, a portable-artifact smoke test, coverage with no arbitrary threshold. **Do not weaken or bypass a failed gate.** Tests are required for database migrations, autosave and recovery, backup and restore, import and sanitisation, attachment validation and path safety, and API validation and error handling.

**GitHub Actions (�12).** GitHub-hosted runners; the portable Windows executable on `windows-latest`. Pinned Bun; frozen lockfile. **The user's PC needs no Bun, Node or compiler installed.** A portable ZIP artifact. **A required gate failure must block publication.** Least-privilege `permissions`.

**Documentation (�13).** Update documentation when behaviour or architecture changes. Keep `README.md` concise. Relative links. Mermaid for relationship diagrams. Add or update an ADR for architectural decisions. **Never mark implementation complete when only documentation exists.** Run `bun scripts/verify-docs.ts` whenever documentation or links change. **"Verified" requires full enforcement, and only for the claim as written** � a partial control is enumerated half by half, naming a file for each. **A regression test can go red for a reason unrelated to the defect, so the red must be red for the intended reason.**

## 22. Executive Summary

### RTWiki in one paragraph

RTWiki is an offline-first, single-user block-based wiki that runs entirely on one Windows PC with no accounts, no internet and no cloud. It is built on Bun, Hono and `bun:sqlite` with hand-written SQL and no ORM; a React 19 and Mantine 9 frontend with a BlockNote rich editor, a micromark Markdown pipeline, a calendar with recurrence and notifications, and image and document attachments stored as database BLOBs. A Tauri 2 shell wraps it for Windows. It is currently mid-implementation of backup and restore, the feature that protects everything else.

### Current architecture

A modular monolith in one Bun process. React state at the root drives workspaces, with no router and no state library. Requests flow through thin API clients to Hono routes, then services, then repositories, then SQLite in WAL mode. Four middleware layers sit in front of every route, the important two being a Host allowlist and an origin check on unsafe methods. All paths derive from the executable's directory. There is no authentication by design; the loopback bind plus those two checks are the security model. `src/shared/constants/index.ts` is the single source for every repeated value.

### Current feature set

Pages with hierarchy and drag-reorder; BlockNote rich editing with formula, diagram, mind-map and callout blocks; Markdown pages with GFM, maths, `:::columns` and Mermaid fences; diagram and mind-map pages; a calendar with weekly-or-one-off recurrence, reminders and notifications; image and document attachments; `LIKE`-based search with a quick finder; wiki links and backlinks; trash; tabs; light and dark themes; autosave; a settings workspace; spellcheck; keyboard shortcuts; a desktop shell; and backup and restore.

### Current development phase

Backup and restore, on `feat/backup-restore`, four commits ahead of `docs/security-claims` and unmerged. The tree is clean and all four gates pass. `main` is far behind at a formatting commit, so **this branch is not on any release path** � merging it is a decision someone must take deliberately.

### What is currently being worked on

Backup and restore. The mechanism is sound and the two subtlest defects � WAL sidecars and close-before-move � were caught and fixed. Two gaps remain: **nothing validates a backup after writing it**, and **the browser spec has never passed**, with three failures recorded on disk. The design document also contradicts itself and the code in three places, one of which is stated as measured fact in `AGENTS.md` and did not reproduce.

### What remains

Validate the written backup. Run and fix the browser spec. Reconcile the three documentation defects. Take the 500 MB measurement that decides whether the current spinner is adequate. Then the larger unplanned work: the import pipeline, blocked on the block registry, and the ZIP dependency it needs.

### Major risks and unknowns

- **The project's documentation has a documented history of describing things that do not exist** � eight documents were found asserting an architecture that was never built, and `README.md` still names two uninstalled libraries. **Where a document and the code disagree, the code is right.** This is the single most important thing for a new agent to internalise.
- **Backup and restore is unproven in a browser.** The one feature whose failure destroys a user's only copy has never been exercised end to end.
- **Nothing validates a backup after writing it.** A corrupt backup would be discovered at restore time.
- **Test harness debt.** Two shared-global hazards � the shared JSDOM and the `mock.module` leak � are worked around rather than fixed and will keep costing time.
- **The block registry is unbuilt**, and the import pipeline depends on it. `AGENTS.md` �6 calls the current central list a rule violation.
- **Search will not scale** � `LIKE` over a 50-row window, with FTS5 provisioned and unused.
- **The desktop shell has never been run** on any machine a developer has used.
- **A scope contradiction in `ROADMAP.md`:** five approved slices each forbid adding tests, which `AGENTS.md` �11 requires. Only the owner can resolve it.
- **The security posture described in `AGENTS.md` �9 and the `ROADMAP.md` slices predate recent fixes** and neither has been reconciled.

### Information that could not be verified

- **Desktop behaviour of any kind.** No Rust toolchain; `build:desktop` has never run here.
- **The executed browser test count and pass rate.** 387 `test()` calls are declared across 40 specs, but no full Playwright run has been executed on this branch.
- **Backup performance at scale.** Every timing in this inspection came from a 6-page or 19-page database and is meaningless for a real wiki. **The 500 MB measurement has not been taken.**
- **The documented truncation behaviour.** `AGENTS.md` states 30% truncation throws and 60% returns rows. I measured 30%, 60% and 90% and **all three threw**. The claim did not reproduce; the code is correct either way.
- **Whether the FTS5 table is maintained correctly.** It has no triggers at all and is never queried, so nothing exercises it.
- **The intended relationship between `docs/security-claims`, `main` and `develop`.** `main` sits at a formatting commit while substantial work lives on a feature branch, and no document explains the intended integration path.
- **The calendar's browser-level behaviour.** There is no calendar spec, so the notifier and recurrence are covered by unit tests only.
